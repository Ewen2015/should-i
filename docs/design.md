# 设计笔记

这份产品里几乎每一个决定都是量出来的，不是选出来的。下面是决定本身、支撑它的数字，以及被实测否决的做法。

看懂它们的顺序：X 怎么被说出来 → 一道题里有什么 → 为什么要问两遍 → 为什么用 noul 而不是 Choice → 为什么切成 11 批 → 那 12 个锚。

## 输入那一句必须被改写

`state` 里是读者原话，加上一句英文；**没有任何一道题说「it」是什么**。
这是省钱的必要条件，不是疏忽：决定写在 state 里一次，510 道题就都能指向它；
写进题面就是把它重复 510 遍。

但在这之前，X 是隐式的。「人类要成为一个星际文明吗？」本身既没说「支持成为」，
也没说是「支持还是反对成为」——而下面每一个数字都是「对 X 的支持度」。
所以有一次 DeepSeek 调用把 X 说出来：

- **方向必须是「做」的那一边。** 下游问的是「指向做还是不做」，
  而页面上「支持 X」显示成「做」。所以「该不该禁止短视频？」要写成
  **「你支持禁止短视频吗？」**，不能写成「你支持不禁止短视频吗？」——反了就是把 0 和 1 对调。
  这条写在 system prompt 里，也有测试守着。
- **形状要检查。** 一段散文会变成页面上的一整段话，一个**答案**会把产品的结论印在地图上面。
  `frame_en_ok()` 要求英文那行是一句话、以问号结尾、并且点名了 X
  （「Do you support it?」正是这一行要修掉的悬空代词）。不合格就退回只用原文。
- **原文照传。** 改写可以错，原文不会，所以两行都在 state 里；页面上改写下面是原话，
  小字一行截断。
- **它必须阻塞，而且阻塞多久是量出来的。** 英文那行要在 11 次付费请求之前拿到：没有它，
  510 道题里的「it」就没有名字，11 次请求全在问一件没人说得清的事。所以运行在这里等。
  等多久量过三次：缓存命中 **0.006s**、热的一次 **1.03s**、**冷的一次 7.12s**；
  倒计时本身 **3.52s**（3 秒 + 「判」那一拍）。于是快的那两次藏在倒计时里，慢的那一次
  藏不住——原来的倒计时不管后面发生了什么，都在固定一拍之后消失，
  实测倒计时结束到第一个 Jev 请求发出之间
  **空了 2.54 秒**，屏幕上什么都没有。现在倒计时最后一拍要等运行就绪才抬起来，
  超过 2 秒开始报秒数（7 秒那一次读作 `判 / 正在核对题干 · 已等 5 秒`）。

  上限原来是 5 秒，**比它要等的那个答案还短**：冷启动那一次就因此丢掉了 state 里的
  `the_same_decision_in_english`，11 次付费请求对着一个没有名字的「it」判分——
  这比等得久糟得多，因为没有人看得出来。现在上限 20 秒（观测到最坏值的约三倍），
  而且真到了上限页面会直说英文题干没拿回来，不留一行空白。

## 每个人是怎么被问的：只有身份，没有观点

发给 Jev 的每一道题，除了人名、生卒年、文化圈，**没有一句关于他想过什么**：

```
老子 Laozi (571B–471B, China). On the user's decision, would he say:
    support it, or not support it?     criteria {"true":"support it",...}
```

中英文名都留是有用的：英文维基是这个名录的来源，对 Kaṇāda、Kumārila Bhaṭṭa 这种人，
中文名单独拿出来是个更弱的抓手。

**那行「框架概括」是量出来该删的，不是偏好。** 原来每题都带一句
`老子（前571–前471，中国）的框架是：无为；不要强推，让事情自己落定`。
删掉它，平均每个人动 **0.0555**，是噪声地板（0.0061）的 **9 倍**，2613 人里 **627 人跨过 0.5**。
也就是说：那句话不是帮模型回忆的提示，**它就是被测量的东西本身**。

同一批实测还说明两件事：

| 第二轮怎么写 | r | 平均差 |
| --- | --- | --- |
| 重复这份名单 | 0.990 | 0.013 |
| 「上面那个人」 | **0.552** | 0.071（差 5 倍） |

所以每个人都被完整地重新点名一遍，哪怕同一个人在同一批里问两遍。
省这点 token 的代价是判断基本不可用。

## 为什么每个人问两遍

只问「它指向做还是不做」时，输出 **92% 说做**。听起来像个结论，其实里面混着
「模型更喜欢 `true` 这个选项」的倾向。反过来问一遍（把「不做」放在 `true`），取中间：

| 同一批 24 个框架 | 说「做」的比例 |
| --- | --- |
| 正问（`true` = 做） | 92% |
| **再问一遍同样的**（噪声底） | 88% |
| 反问（`true` = 不做） | 50% |
| **两遍取中间** | **63%** |

重复问同一句，`|A − A′|` 平均 **0.012**、最大 0.030；换个方向问，`|A − B|` 平均 **0.258**、
最大 0.720，24 个人里 **14 个的判断直接翻转**。噪声底和真实位移差一个数量级，
所以弯曲是真的。取中间是 `(正向 − 反向 + 1) / 2`：两遍读法一致时正好落在 0.5，
一个读不出方向的框架落在栅栏上，而不是被这个偏推到某一边。

## 为什么是 noul，不是 Choice

**Choice 的概率是和为 1 的帧内份额，不能跨批次相加。** 它问的是「这 255 个里**哪一个是**」，
是一次竞争：255 个选项里只有 3–6 个拿到概率，其余两百多个是 0。
**0 乘任何标定系数还是 0**——锚只能重新标定，不能把 0 救回成一个位置。
实测过：同样两组人加 12 个共同锚，两组之间的换算系数差 **4.1 倍**（0.29 vs 1.17），
根本不存在一个统一的系数。

**noul 是一句独立判断，不和同批的人竞争。** 同样 20 个人的框架，放进两个完全不同时代背景的
255 人名单里分别打分：

| | |
| --- | --- |
| Pearson r | **0.990** |
| \|最大差\| | 0.030 |
| \|平均差\| | 0.013 |

所以 noul 的分数天生跨批次可比，2578 个人可以切成 11 批分别问。

## 255 和 11 批

`255` 是 Choice/Noul 单次请求的硬上限。2578 个人 ÷ 255 ≈ 10.11，所以是 **11 批**。
每批正好 255 个选项，一批都不浪费；名录不足 255 时一批都不发。

**为什么不把名录做大。** 查得到的历史人物池子（英维条目 + 出生年，46 种职业）
一共约 **12,102 人**，是现在这 2578 人的五倍。12,102 位就是 **48 批**，一次提问约 55 万
输入 token，动画也有 48 段，用户看不到一半就会关掉。11 批是覆盖面和体验之间的折中。
真要全量，正确的做法是**两遍选择**（第一遍 255 个选项选「哪一段名单」，第二遍在那一段里排序）
——TypeSafe cookbook 里 `semantic_find.md` 写的就是这个模式。这一步还没做。

## 尺子上那 12 个人

既然要分 11 批发，就得把「各批可比」做成**每次都能当场量出来的数**，而不是一句承诺。

- **每一批正好 255 个选项**（243 个名录里的人 + 同样这 12 个锚），硬约定不破。
- **12 个锚出现在全部 11 批里**，所以同一个人在 11 个不同的「公司」里各被问一遍，
  他的 11 个读数的最大差就是真正的跨请求误差。
- **最后一批贴住现在**，因此和前一批重叠，重叠的人被两条不同的切片各测一次，
  是第二种、免费的交叉检验。重复测量**取平均**，不是后来者覆盖。

实测（一次完整运行）：

| | |
| --- | --- |
| 12 根锚跨 11 批的差 | 最大 **0.055**，平均 **0.021** |
| 重叠的人两次的差 | 最大 **0.025** |
| token | 约 38–41 万输入 / 12 万输出 |
| 用时 | Jev 11 批 **约 19s**，4 条并发，与动画并行 |
| 其中题干改写 | 串行在 11 批之前：**0.006s** 缓存／**1.03s** 热／**7.12s** 冷 |

**加锚会不会把别人挤歪？** 这是这个设计唯一的真风险，所以单独量过：同一批 243 个古代人，
**单独问一遍** vs **把这 12 个锚塞进去再问一遍**——r **0.996**，平均差 **0.008**，
最大差 **0.030**。锚是校准而不是扰动，它占掉每批 12 个名额（约 5% 的成本）。

**这 12 个是默认值，不是设计。** 任何一组名录里的人都能当锚。标题栏上的
**「锚点 12 人」**按钮可以搜名字（中文、拼音、英文都行）换人；
「确认」只记下人选、不发请求，「确认并重跑」才会花那 11 次。
